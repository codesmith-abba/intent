# AI Repair

Phase 13 adds a bounded repair loop after generation and validation. It does not create a second generation pipeline.

## Pipeline position

```text
.ITL source
→ Lexer
→ Parser
→ AST
→ Semantic Analysis
→ GIR
→ Dependency Graph
→ Change Detection
→ Diff Analysis
→ Build Plan
→ Scheduler
→ AI Generation
→ Validation
→ Repair (when validation fails)
→ Validation
→ Emit
```

## Scope

Repair is scoped to the failed `BuildItem`. The repair request contains the existing `GenerationRequest`, the failed output, validation failures, dependencies, target/framework, and repair constraints. Unrelated build units are never regenerated by the repair subsystem.

## Provider boundary

`RepairProvider` is intentionally separate from the existing `GenerationProvider`. A provider receives a `RepairRequest` and deterministic repair prompt and returns `RepairProviderResponse`. No external AI service is required by the compiler.

## Retry policy

`RepairPolicy(max_attempts=3)` provides a configurable upper bound. Every attempt is validated before another attempt is allowed. A provider exception, unchanged output, or exhausted retry budget produces a structured `RepairResult` failure.

A valid output is never repaired. The unchanged valid-output path returns success without invoking a provider.

## Build integration

`BuildExecutor` accepts an optional `Repairer`. When normal validation fails, the executor invokes the repairer for that same build unit. A successful repair becomes a normal `BuildResultStatus.SUCCESS` with its final validation report. A failed repair remains `FAILED` and retains the latest output/report.

This preserves the existing scheduler, build results, validation pipeline, and generation backend instead of introducing another build pipeline.

## Testing

Phase 13 tests cover successful repair, retry exhaustion, validation after every repair, provider failure, unchanged valid output, unchanged repair output, multiple validation issues, and BuildExecutor integration.
